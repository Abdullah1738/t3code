# harness-cli

Keeps pinned, verified Claude Code and Codex CLIs for Robob. Each tool lives under
`~/.robob/harness-cli/<tool>/<version>/` (read-only, never overwritten). A `current`
symlink per tool is the `binaryPath` Robob's `claudeAgent`, `codex` and `codex-cu`
instances run. Promotion swaps that symlink atomically; rollback points it back at the
last known good version.

Stdlib Python only (`/opt/homebrew/bin/python3`). Source: this folder. Installed copy:
`~/.local/share/harness-cli` (evaluator installs it with `deploy.zsh harness-cli`).

## Commands

```sh
harness_cli.py discover                  # npm view both packages (exempt, read-only); records candidates
harness_cli.py stage <tool> <version>    # npm pack (exempt), sha512 vs npm, extract read-only
harness_cli.py canary <tool> <version>   # throwaway homes + 9router prompts + memory-off canary
harness_cli.py promote <tool> <version>  # canary-gated atomic switch of current
harness_cli.py rollback <tool>           # current -> lastKnownGood
harness_cli.py rotate-codex [--when-idle]
harness_cli.py status
harness_cli.py auto                      # the daily job (launchd 06:00 Dubai)
harness_cli.py --before-release          # flag: discover + stage + canary both; prints the pins
```

`<tool>` is `claude` or `codex`. Every step appends one line to
`~/.robob/harness-cli/records.jsonl` (tool, version, binary sha256, Robob build, harness-home
config hashes, result). State lives in `~/.robob/harness-cli/state.json`.

## Version rules

- npm's global `min-release-age=7` is bypassed only by `--min-release-age=0` on the
  Claude Code and Codex packages (standing exception, DECISIONS 6). `~/.npmrc` is never edited.
- Integrity: the tarball's sha512 must equal `npm view <pkg>@<v> dist.integrity`. A mismatch
  stops the stage and writes nothing.
- Minimums come from `apps/server/src/provider/model-manifest.json`: the driver minimum for
  each CLI, and each model's minimum (Haiku 5.5 needs Claude 2.1.293; Astra and Sol need Codex
  0.153). A version below one is refused before download.
- A staged version must report exactly the version it was staged as.
- Claude uses the native `@anthropic-ai/claude-code-darwin-arm64` binary, and Codex uses
  `@openai/codex@<v>-darwin-arm64`.

## Canary (every promotion)

Runs in a throwaway HOME, with homes generated by `harness-homes generate|check --home-root`
(card B1) and a loopback proxy that records every request body and forwards to 9router
(`127.0.0.1:20128`). The key comes from `NINEROUTER_KEY` and is never printed.

- Claude: one prompt each for `claude-opus-5-5` and `claude-haiku-5-5` (`--effort low`).
- Codex: one `codex exec` each for `gpt-6-astra` and `gpt-6.1-sol`.
- Memory-off (DECISIONS 15, hard requirement): Claude gets a seeded `MEMORY.md` with a canary
  word; the word must not appear in any request body. Codex must create no `memories`,
  `memories_extensions` or `memories_1.sqlite` artifact.
- Any failure, or a missing memory check, means no promotion. The record shows why.

## Rotation rules

- **Claude:** promote changes `binaryPath` for new processes only. Existing queries keep their
  binary. No restart, so promotion is safe to run automatically.
- **Codex:** the shared app-server keeps running the old binary. Promotion marks
  `rotationPending`. The rotation happens at the next Robob release/restart, or through
  `rotate-codex --when-idle`, which needs all of these:
  1. `autoRotateCodex: true` in `state.json`. This is Abdullah's standing OK; the default is `false`.
  2. The recovery snapshot route `GET /api/ardud/control/recovery/snapshot` (card E7). If the
     route is missing, the rotation is skipped with a message.
  3. No Codex thread with a running run, held work or a pending request for 5 minutes. A busy
     Codex is never rotated; the wait gives up after 30 minutes and the next run tries again.
  4. Then the provider refresh (WS RPC `server.refreshProviders {instanceId}`).

  The snapshot field names the check reads (`threads[].provider`, `runningRun`, `heldWork`,
  `pendingRequest`) are the contract this job expects from E7. E7 is not on the fork yet, so
  confirm them against E7 before enabling `autoRotateCodex`.

  The provider refresh itself is not wired in this build: `refresh_codex_provider` raises, so
  rotation stays pending. The evaluator wires the WS call when E7 ships (catalog-guard's
  `refreshProviders()` in `~/.local/share/catalog-guard/lib/io.mjs` is the reference).

## Daily job

`launchd/com.ardud.harness-cli.plist` runs `harness_cli.py auto` at 06:00 Dubai:
discover, stage, canary, promote Claude when the canary passes. Codex stops at
"promoted, rotation pending" unless `autoRotateCodex` is on. A new version gets one
Telegram notice (key `harness-cli:<tool>:<version>`), whether it was promoted or a canary
failed. The notice command is `HARNESS_CLI_NOTIFY`, overridable for tests.

## Install

```sh
integrations/deploy.zsh harness-cli --with-agent   # evaluator step, after review and merge
integrations/harness-cli/install.zsh --check       # drift check, no write
```

Deploying does not stage or promote anything by itself. The first run happens at the first
06:00, or when the evaluator runs `harness_cli.py --before-release` for the release.

## Tests

```sh
cd integrations/harness-cli && /opt/homebrew/bin/python3 -m unittest discover -s tests -v
```

Every path lives in a temp dir; a fake `npm` answers `view` and `pack`; fake CLI binaries print
their version and "OK"; a fake proxy records bodies. Tests never touch `~/.robob`, `~/.claude`,
`~/.codex` or the network.
