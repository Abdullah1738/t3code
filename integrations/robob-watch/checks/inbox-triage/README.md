# Inbox triage

Ordinary INBOX mail, WhatsApp and iMessage/SMS triage runs every **300 seconds**. A separate **15-second** inbox-triage-fastpath check reads bank/security mail and iMessage/SMS without a model or an agent turn. SIM/eSIM changes, Apple/Google/bank new-device logins, and card debits of AED 1,000 or equivalent send a neutral notice directly through the existing Telegram and iMessage bridge CLIs. Unexpected OTPs/sign-in links are logged only by the fast path and follow ordinary triage filters and preferences. Free filters precede Haiku classification in batches of 16, with one retry for transient failures. Only hits wake the live owner iMessage session for full-message review. Urgent security, crypto withdrawal, card and driver items also go to Telegram when bridge health says the chat cannot process them. There is no quiet window.

## Install or update

Requires the existing robob-watch runner, mailsearch/mail_oauth authentication, wa-db helper, read access to the chat stores and the existing OpenRouter key. Configure local identities before enabling a fresh installation:

1. Create `~/Documents/assistant/inbox-triage/settings.json` from `settings.template.json`. Set the self WhatsApp JID, group mention names and excluded iMessage chat IDs/identifiers (self-chat and chats already handled elsewhere); set `configured` to true. Chats with a Robob line in them are skipped by themselves: the line comes from the bridge's `sendblueNumber` in `~/.config/spectrum-bridge/config.json`, plus any extra numbers in `robob_lines`.
2. Deploy the matching `app-api-cli` source first, then from this directory run `/usr/bin/python3 -B install.py`. The installer checks that the Careem OTP and commerce payment callers have the registry wiring before enabling the fast watcher. It copies only the named source files and registers both watcher definitions. Both watcher directories receive the same source files. The fast check runs its local `check.sh --fast-only`, including in scratch tests, with its own cursors and check lock and a shared notification ledger with the outage path. Missing prefs/noise files are seeded from templates; existing files are preserved.
3. Run `unset BUN_INSPECT` then `robob-watch test inbox-triage` and `robob-watch show inbox-triage`.

This package lives under `checks/` because `integrations/deploy.zsh robob-watch` intentionally excludes the live `watchers/` state tree. Its dedicated installer updates only this check, not the runner or unrelated integrations. No service restart is needed: the runner reads the definition each tick and each check starts a fresh process.

The installer waits for both checks' `check.lock` files (65 seconds maximum), atomically replaces source files and preserves the lock inode. It never copies/deletes cursors, queues, outboxes, run logs, credentials or local settings/preferences. Existing paused state is preserved. New installs baseline at their first run; upgrades keep all cursors.

## Execution bounds and recovery

- Accounts run concurrently, each with a 25-second total budget including one transient retry. Mail workers have a 19-second alarm and save fully processed prefixes when a batch runs long.
- Classification has a 20-second wall-clock budget, cut so it answers by second 44 of the run. The chat follow-up checks stop starting items at seconds 32 (before classifying) and 46 (after); items they don't reach stay candidates and `answer_check_errors` says so. With no time left the batch goes to manual review without a call. The runner kills the whole check process group at 60 seconds, well below the five-minute cadence.
- `check.lock` prevents overlap; a separate `dry-run.lock` means replay diagnostics cannot suppress a scheduled check. Contention exits 75 so the runner cannot overwrite a prior output acknowledgement. Installation registers paused under the lock and resumes after release.
- OTP context is checked across the whole message before redacting preview fields. FETCH literals must have valid UIDs; omitted messages are confirmed expunged before the cursor can advance past them.
- Atomic cursor + candidate queue writes happen before classification. Hits commit to an outbox before stdout; the runner's `.run-ok` acknowledges them. Failed sources retain their last successful cursor. Model failures become manual-review candidates without a second call.
- A chat message is dropped once it has been dealt with: its chat has a Robob line in it (`robob_chat`), or it was answered. In a direct chat a later message or tapback from the owner, or from a Robob line, counts. In a group only a swipe reply or tapback on that very message counts, since he may be talking to someone else. Failed, unsent, retracted, revoked or removed follow-ups never count. Both are checked against the live stores when the batch is built, again after classifying, and once more if an unacknowledged wake is replayed (the replayed wake is rebuilt from the batch file as it stands), so a candidate that was already queued still gets dropped. If that replay check took more than 3 s and cleared the whole batch, the run stops there and the next run collects. Mail has no such check. A store that can't be read drops nothing.
- The classifier also sees `live_work`: open payments from `commerce open-flows --minutes 60` and whether a phone task holds `~/.local/share/phone-lock/priority-hold`, and each message lists the payments it surely came after (`after_payments`, from exact times). A bank or card prompt counts as likely ours only when it lists that payment and nothing in it contradicts it; a phone task alone, a prompt that didn't come after any payment, or a mismatch needs checking against order work. The batch and the wake carry the same list. If either can't be read it says so, and a bank prompt is never called "not ours".
- Bank payment deadlines and scheduled autopays are parsed before charge checks and the general classifier, including bank mail with bulk headers. They record source IDs in money-cases; successes close matching rows. A tracking write that cannot finish stays queued. Dry replays only detect and never write the money books. Payment reminders are emitted by money-cases alone.
- Subscription renewals on a card recorded dead by `money-cases card-dead` become money cases before classification and drop as `renewal_case`, including duplicate notices for an existing or closed case. Detection requires a currency/amount, a date linked to the renewal wording and card last four. Full mail and SMS text is parsed before preview truncation, and its rejection is retained too. Bulk/promotion headers are applied after the bounded body read so a generic subject cannot hide a renewal; nonrenewal mail still gets the usual filters. Scratch runs copy `cards.json` and `subscriptions.json` along with the money books; dry replays learn entries and create cases only in `scratch-renewals`, never in the live books, and use the replay's unbounded tracking budget. Live-card renewals learn register entries and stay with ordinary triage. Card-charge matching uses the same register and advances its next renewal only in a non-dry run; amount, merchant, card, currency or date mismatches keep the ordinary charge checks.
- Card charge and decline alerts (iMessage SMS or bank mail) go through `../money-cases` first, until second 24 of the run (owner rule, nightly review 24 Oct: find the receipt or his own words before asking, and wait for the receipt from a merchant he already pays). Explained, waiting, already-asked and money-case alerts drop (`charge_explained`, `charge_wait`, `charge_asked`, `charge_case`), and the bank's mail copy of an SMS already passed on drops as asked. A fresh charge with nothing found stays queued for five minutes in case its receipt comes with it (`held_for_receipt`); one the time budget didn't reach waits up to 30 minutes. The rest reach the classifier with a `charge_check` note and go to the agent even if it skips them. Runs outside the live watcher use a copy of the money books in their own folder (`scratch-money`). If money-cases can't be loaded or read, the alert goes to the classifier as before and `charge_check_errors` says why. This needs the money-cases package installed next to this one.
- Mail reads oldest UIDs first in chunks of eight, up to 32 per account per run. Completed chunks persist their cursor and redacted candidates together in `mail-progress-<account>.json`; a killed fetch replays that checkpoint into the main queue before reading more. Credential preparation runs in its own process session, so fetch and runner timeouts cannot interrupt its refresh. An IMAP auth rejection gets one isolated refresh and fetch retry within the original account budget. A separate watcher-owned lock shared by both checks permits only one credential process per account; other runs use a valid cached token or report `refresh_inflight` with its age. Auth healing never reuses an already rejected cached token. `runs.jsonl` separates credential, connect and fetch diagnostics by account.
- A classifier window shorter than eight seconds leaves candidates queued. Three deferred attempts or 15 minutes triggers manual review anyway. `deferred_count` and `oldest_deferred_age_s` show pending deferrals, and classifier budget, elapsed time and attempt counts distinguish starvation from endpoint failure.
- A run with at least one fully readable source exits 0; partial failures print `inbox-triage degraded: <source>: <error>` to stderr and retain failed cursors. Only a run with no readable sources exits 1, even if it queues an event (the durable outbox replays it next tick). `triage.py --fast-only` uses the same source rule; delivery failures remain pending independently. `fastpath.py` itself only classifies items.
- Source health lives in `cursor.json` (`source_health`). Three consecutive failures or five in an hour trigger a Telegram notice naming the source. Provider/network failures (timeouts, TLS handshakes, connection resets/refusals, temporary DNS) get one notice per outage, one attention escalation after 3 continuous hours, and one recovery notice. Other errors, including auth and parsing, keep the 6-hour repeat interval. Recovery resets the continuous outage clock while the last-notice cooldown survives for 6 hours; rolling failure counts still detect flapping. The 3-hour escalation follows the new continuous outage even when its initial notice is suppressed by that cooldown. Each notice's key and text are saved (`health_pending`) before sending; retries reuse them, and a pending notice expires after 6 hours. Partial source outages do not enter the runner's FAILING/backoff/alert path. Only the live watcher sends; `robob-watch test` records `health_alerts_skipped` instead.
- Urgent Telegram alerts use a three-second bridge health probe, stable per-item keys and 48-hour sent bookkeeping. The batch and wake mark successful sends so the agent follows up only if something changed. During the outage, selected hits stay queued while collection continues; their wake waits for chat recovery, avoiding a second Telegram alert through the runner fallback. Pending Telegram payloads keep their original text until acknowledged. Scratch and dry runs record would-send IDs. Withdrawal candidates check the newest same-reference status in the batch/queue, then the last 24 hours of the mail archive under a shared three-second budget; unavailable lookups say `not checked`. No watcher context change is needed.
- Fast alerts persist only a fixed summary, amount and card last four, never a copied message body, OTP value or sign-in link. The two senders share per-message keys and a locked delivery ledger (`urgent-delivery.json`); each channel retries its original text independently. iMessage is marked delivered only after the bridge outbox reports a transport send; queue acceptance stays pending. A cancelled operation gets a new attempt key only when its attempt count is zero and it has no provider id, proving no dispatch occurred. Ambiguous or already-dispatched operations keep their key and wait for reconciliation. An acknowledged fast security item skips the ordinary batch; large debits still pass through money-cases, and any later wake says the neutral notice was already sent. Pausing `inbox-triage-fastpath` restores ordinary batch handling. The fast check bounds credential waits plus mail reads to 14 seconds/account and direct delivery to second 38; with a 15-second polling interval it targets arrival-to-send under a minute while sources and transports are available. Delivery failures stay pending, and source-health alerts cover repeated read failures without backing off other security sources.
- Careem's OTP request and Noon's journalled financial sends register their exact known SMS sender before dispatch. The bank sender follows the selected card (2342: Emirates NBD; 9546: Mashreq); unknown cards never create a broad expectation. The shared writer stores only sender, receiving account and time in local `inflight-actions.json`. An action must precede the incoming message by at most 10 minutes; phone locks and unrelated senders never mark a code or link expected. Other explicit request callers can register with `/usr/bin/python3 -B triage.py --expect-auth support@example.test --account gmail`; absent evidence, the code/link is treated as unexpected. Registry failure while the fast watcher is enabled stops the request before dispatch.
- AED and the fixed USD/SAR/QAR/BHD/OMR pegs work without configuration. For other currencies, set current AED-per-unit values in private `settings.json` under `fastpath_aed_rates` (decimal strings, e.g. a rate supplied by your bank). Unsupported/unconfigured currencies retain ordinary money-case triage rather than guessing an exchange rate.
- Messages and context are untrusted data. Only the owner alerts described above send messages; no payments or read-flag mutations happen in this check.

Local data: `~/Documents/assistant/inbox-triage/{prefs.md,noise.json,settings.json,runs.jsonl,batches/}`. State: `~/.local/share/robob-watch/watchers/inbox-triage/`. Keep both outside git. Only generic templates belong here.

## Verify

```sh
ROBOB_TEST=1 /usr/bin/python3 -B -m unittest -v test_triage.py test_urgent.py test_mail_retry.py test_backlog.py test_install.py test_lock.py test_fastpath.py
unset BUN_INSPECT
robob-watch test inbox-triage
robob-watch test inbox-triage-fastpath
```

A historical replay (mail, WhatsApp and iMessage) does not advance live cursors or send notifications. It reads exactly the requested window (up to 20,000 rows per chat source, and says so in `source_errors` if it stops early) and classifies every candidate, 16 at a time. The report lists every dropped id with its reason:

```sh
triage_replay_dir=$(mktemp -d)
WATCH_DIR="$triage_replay_dir" TOOLLOG_DIR="$triage_replay_dir/tool-logs" \
  /usr/bin/python3 -B triage.py --dry-run-hours 2 --report "$triage_replay_dir/replay.json"
```

Dry runs require an explicit scratch `WATCH_DIR` and refuse the live watch directory.

Usage and cost are logged per real run; empty batches have no model cost. The ordinary schedule has up to 288 checks/day, not necessarily 288 model calls. The independent fast poll makes no model calls. Review actual token/USD usage before estimating a monthly total.
